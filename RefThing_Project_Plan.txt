========================================================================
REFTHING — PROJECT PLAN (v2)
A high-performance, web-based reference board (PureRef clone)
========================================================================

OVERVIEW
--------------------------------------------------------------------
RefThing is a browser-based reference board built to handle massive
boards (thousands of items) at 60fps, with better organization,
crash-safety, and clean extensibility to new content types (3D
models, video, audio, web embeds), while staying a faithful clone of
PureRef's actual interaction model — not a reinterpretation of it.

Core architectural principle: React owns the UI chrome. It does NOT
render the canvas itself. The canvas is a separate WebGL rendering
layer with its own scene graph, mounted once and updated imperatively.

Core interaction principle: PureRef's defining trait is near-zero UI.
Every common action is a mouse gesture (with a modifier key) that
becomes obvious after one use. Anything uncommon lives in the
right-click context menu. RefThing keeps this exactly — no visible
toolbars for actions PureRef handles with a gesture, no free-form
transform handles, no invented interaction concepts. Bindings are
config data, not hardcoded logic, mirroring PureRef's own philosophy
that nearly every action is a rebindable shortcut.

- FPS/latency HUD (dev-only) for perf regression tracking


========================================================================
CONTROL SCHEME & INTERACTION PHILOSOPHY
========================================================================
This is a direct clone of PureRef's real interaction model, confirmed
against the official handbook — not a custom design. No drag
threshold exists for item movement; click-and-drag on an item moves
it immediately. No free-form transform handles — every scale/rotate/
flip anchor point is determined by which modifier key is held, not by
which handle the user drags. The transform gizmo only appears on
selection; there is no persistent toolbar.

MOUSE (no drag threshold on item movement)
--------------------------------------------------------------------
Left click                       Select item
Left click + drag, on item       Move item(s) — immediate, no threshold
Left click + drag, empty canvas  Box/rubber-band select
Shift + left click               Add/remove from multi-selection
Middle mouse + drag              Pan the canvas
Right click, no drag             Context menu
Right click + drag                Move the window
Double-click, locked group        Enter group, select child under cursor
Double-click, selected image      Zoom in on it (double-click again to return)
Double-click, empty canvas        Zoom to fit everything
Scroll wheel                      Zoom, centered on cursor

The ONE real threshold in the whole scheme: right-click specifically
distinguishes "open context menu" from "start moving the window" via
a configurable pixel distance (PureRef exposes this in Settings as
"Move window threshold"). This is scoped to that one button only —
not a general interaction-state-machine concept applied everywhere.

MODIFIER KEYS (anchor points are action-specified, not free-transform)
--------------------------------------------------------------------
Ctrl/Cmd + drag on image          Rotate
Ctrl+Shift + drag                 Rotate, snapped to nearest 45 degrees
Alt + drag a corner handle        Scale from center (item stays put)
Shift+Alt + drag (multi-select)   Rotate/scale each item around its own center
Alt+Shift + drag                  Flip along the drag axis
Shift + drag                      Constrain movement to a straight line
Shift+Space + drag                Snap-move to nearest edges of other items
Z + drag                          Alternate zoom gesture

NOTE TEXT EDITING (resolved — no threshold, no state machine)
--------------------------------------------------------------------
Reuses PureRef's own double-click convention (already used to enter
a locked group and to zoom a selected image) instead of inventing a
new interaction concept:
- Single click / click-drag on a note -> select / move it. Identical
  code path to an image — no special casing.
- Double-click on a note -> enter text edit mode. Native browser
  dblclick event handles the disambiguation; no custom timing logic
  needed.
- While editing: pointer events go to the pretext editor; click
  elsewhere or Escape commits the edit and exits back to normal
  selected/movable state.

ITEM DRAG FIX (bug, not a control-scheme question)
--------------------------------------------------------------------
Root cause of "items change position instead of moving with the
drag": likely absolute position assignment (item.x = pointerWorldX)
instead of delta-based movement, and/or a missing or duplicated
screen-to-world conversion when panned/zoomed. Fix:
  on pointerdown: dragStartWorld = screenToWorld(pointer); itemStartPos = item.position (snapshot only)
  on pointermove: delta = screenToWorld(pointer) - dragStartWorld; item.position = itemStartPos + delta
Never assign item.position directly to the converted pointer position.
Ensure exactly ONE screenToWorld()/worldToScreen() utility is used by
the renderer, the DOM overlay, and the drag math — no duplicated
transform logic that can drift out of sync.

CONTROL SCHEME AS CONFIG (not hardcoded)
--------------------------------------------------------------------
Store bindings as data, matching PureRef's own approach (nearly every
action is a rebindable shortcut). Example shape:

  [actions.select]
  button = "left"

  [actions.move_item]
  button = "left"
  drag = true
  target = "item"

  [actions.box_select]
  button = "left"
  drag = true
  target = "empty"

  [actions.multi_select_add]
  button = "left"
  modifiers = ["shift"]

  [actions.pan]
  button = "middle"
  drag = true

  [actions.move_window]
  button = "right"
  drag = true

  [actions.context_menu]
  button = "right"
  drag = false

  [actions.rotate]
  button = "left"
  modifiers = ["ctrl"]
  drag = true
  target = "item"

  [actions.rotate_snap]
  button = "left"
  modifiers = ["ctrl", "shift"]
  drag = true
  target = "item"

  [actions.scale_from_center]
  button = "left"
  modifiers = ["alt"]
  drag = true
  target = "handle"

  [actions.flip]
  button = "left"
  modifiers = ["alt", "shift"]
  drag = true
  target = "item"

  [actions.constrain_to_line]
  button = "left"
  modifiers = ["shift"]
  drag = true
  target = "item"

  [actions.enter_note_edit]
  button = "left"
  double_click = true
  target = "note"

  [actions.zoom]
  input = "scroll"

  [actions.zoom_to_fit]
  button = "left"
  double_click = true
  target = "empty"

The dispatcher matches incoming pointer/keyboard events against this
table and fires the matching action. No hidden state machine beyond
what's explicit here. New item types (video, 3D, audio) declare which
of these default actions they respond to without touching input-
handling code — this is also the extension point for type-specific
gestures later (e.g. scrub a video timeline) without special-casing
core dispatch.

KEYBOARD (remaining Phase 4 items)
--------------------------------------------------------------------
Delete / Backspace        Delete selected item(s)
Ctrl/Cmd + G               Group selection
Ctrl/Cmd + Shift + G        Ungroup
Ctrl/Cmd + A                Select all
Ctrl/Cmd + Z                 Undo
Ctrl/Cmd + Shift + Z (or Ctrl+Y)   Redo
Arrow keys                 Nudge selected item(s) by 1px (Shift = larger step)
Escape                     Exit editing -> selected; selected -> deselect

UNDO/REDO CONVENTIONS
--------------------------------------------------------------------
- One undo command per completed gesture (finished drag, finished
  resize, delete, group/ungroup, tag change) — never per-frame during
  a drag.
- Coalesce a full drag (pointerdown -> pointerup) into a single
  command with before/after position.
- Coalesce note text edits into one command per editing session
  (since focus entered until it left), not per keystroke.
- Multi-item operations (e.g. deleting 5 selected items) are a single
  undo command, not 5 separate ones.

PHASE-BY-PHASE PLAN
========================================================================

PHASE 0 — LOCK THE STACK                                    [COMPLETE]
--------------------------------------------------------------------
1. Finalize the library table above.
2. Repo structure: /backend (Rust/Axum), /frontend (React/Vite),
   /sidecar (Node, stubbed), /docs (architecture + onboarding docs).
3. CI: cargo check/test/clippy, frontend lint/build.

PHASE 1 — DATA MODEL & STORAGE                       [COMPLETE 4/4]
--------------------------------------------------------------------
1. Generic item schema (items + item_metadata JSON, not hardcoded
   to "images").
2. SQLite WAL mode.
3. Content-addressed blob storage.
4. Export/import: portable board archive (zip of blobs + manifest).

PHASE 2 — RUST API SURFACE                            [COMPLETE 6/6]
--------------------------------------------------------------------
1. Axum app scaffold: routing, tracing, CORS, error handling.
2. Auth (session or JWT).
3. CRUD endpoints for boards/items/groups/notes/tags.
4. Batch endpoints for moving/updating many items at once.
5. Ingestion endpoint: upload -> hash -> store -> enqueue poster job
   -> return immediately.
6. WebSocket board-diff broadcast: kept as a RECEIVE path only (keeps two
   windows on one board in step, delivers job events such as
   poster_ready). The client writes over REST through a one-in-flight
   batch queue. No collaboration features ride on it (Phase 8 stays cut).

PHASE 3 — THUMBNAIL / IMAGE PYRAMID PIPELINE           [COMPLETE 4/4]
--------------------------------------------------------------------
1. Size pyramid per image via fast_image_resize.
2. Background worker pool (Tokio + Rayon for CPU-bound resize work).
3. Cache-friendly serving path: /blob/{hash}/{size}, immutable headers.
4. Frontend picks pyramid level based on on-screen size.

PHASE 4 — CANVAS RENDERING ENGINE                    [COMPLETE 8/8]
--------------------------------------------------------------------
1. PixiJS Application mounted into a React-managed canvas ref.
2. Spatial index (grid) over node positions (rotation-aware bounds).
3. Viewport culling to visible rect + buffer.
4. Zoom-dependent texture swapping (pyramid level per sprite).
5. Pan/zoom with easing in the render loop (rAF), not React state; DOM
   chrome follows the camera Pixi actually painted each frame.
6. Selection/handle overlay synced to canvas coordinates (one
   screenToWorld utility; pure transform math in canvas/transform.ts).
7. Keyboard shortcuts: Delete, Ctrl+G / Ctrl+Shift+G, Ctrl+A, arrow
   nudge (Shift = x10, bursts coalesce), Escape, undo/redo.
8. Undo/redo command stack: one entry per gesture/command, note edits
   one entry per session, multi-item operations one entry.
Fixed: item drag delta math; note click-vs-edit (double-click only);
rotated resize anchors; rotation accumulation past 360 degrees.

PHASE 5 — CORE PUREREF FEATURE PARITY                [PARTIAL 6/8]
--------------------------------------------------------------------
Done: drag-and-drop/paste/browser-drag ingestion, grouping/ungrouping
+ move-as-unit, group lock + double-click drill-in, grayscale toggle
(GPU shader), color sampler, GIF playback in canvas, flip
(Alt+Shift+drag), opacity, pretext notes painted on the canvas in the
same paint order as images (DOM editor only while editing).
Remaining:
- Group background color/opacity picker UI.
- Smart alignment guides (snap-to-edge while dragging; Shift+Space).
- Crop (context menu).

PHASE 6 — ORGANIZATION FEATURES BEYOND PUREREF        [COMPLETE 5/5]
--------------------------------------------------------------------
Done: tagging system + filter/search bar, SQLite FTS5 full-text
search, duplicate detection (perceptual hashing), color search and
duplicate filter wired into the search bar (state/useBoardFilter.ts),
saved board views.

PHASE 7 — RELIABILITY                                [COMPLETE 4/4]
--------------------------------------------------------------------
1. WAL-mode SQLite + periodic checkpointing.
2. Debounced client-side autosave.
3. Versioned snapshots for rollback.
4. Health-check endpoint verifying blob integrity against hashes.

PHASE 8 — MULTI-DEVICE / COLLABORATION           [REMOVED FROM SCOPE]
--------------------------------------------------------------------
Cut entirely. Not pursuing real-time multi-device sync, presence
indicators, or CRDT conflict resolution. Consequences of the cut:
- No yrs (CRDT) dependency needed.
- WebSocket board-diff broadcast removed from Phase 2 — not building
  a sync layer for now.
- Undo/redo stays a plain linear local command stack (no need to
  reconcile against concurrent remote edits).

PHASE 9 — PERFORMANCE VALIDATION & OFF-MAIN-THREAD   [PARTIAL 3/6]
--------------------------------------------------------------------
Done: synthetic board generator (/dev/board/N, src/dev/synthBoard.ts),
dev-only FPS/latency HUD (src/dev/FpsHud.tsx), perf gate at 20k items
(docs/perf-baseline.md).
Remaining:
- Load-test the ingestion pipeline (bulk upload of thousands of files).
- Move image decode/resize into Web Workers.
- Move the PixiJS render loop into OffscreenCanvas in a worker
  (requires Cross-Origin-Opener-Policy / Cross-Origin-Embedder-Policy
  headers on the Axum server if using SharedArrayBuffer). Weigh this
  against the DOM chrome that must track the canvas every frame.

PHASE 10 — POLISH                                          [NOT STARTED]
--------------------------------------------------------------------
1. anime.js-driven UI chrome transitions.
2. Tailwind design system pass.
3. Keyboard shortcuts matching PureRef muscle memory.
4. Best-effort .pur importer for PureRef 1.x (2.x format is closed —
   stretch goal, not v1).

PHASE 11 — EXTENSIBILITY: MULTI-FORMAT ITEM TYPES          [NOT STARTED]
--------------------------------------------------------------------
Goal: 3D viewports, video, audio (mp3 mini-player), gifs, web embeds,
and arbitrary file formats — without touching core engine code per
new type.

Rendering model:
- POSTER mode (always on): every item has a cheap static WebGL sprite.
  This is what the Phase 4 culling pipeline always deals with.
- LIVE mode (on-demand): the real interactive component (<video>,
  model-viewer/three.js, audio mini-player) mounted as a DOM overlay
  only for items large/focused enough on screen. Cap concurrent live
  instances (~6-10), evict least-recently-focused past the cap.

Data model: generalize to items + item_metadata(JSON) as already
defined in Phase 1 — new types need no schema migration.

Backend pattern — ItemTypeHandler trait: accepted_mime_types(),
extract_metadata(), generate_poster(). One handler per type.

Frontend pattern — ItemRenderer registry: Poster (required, always-
mounted sprite) + Live (optional, on-demand DOM overlay).

Type notes:
- Image:      existing pyramid pipeline (Phase 3).
- Video:      ffmpeg frame extraction -> poster; <video> for live.
- GIF:        decode first frame -> poster; small GIFs can just play
              as an animated WebGL sprite directly.
- 3D model:   offscreen render snapshot (Node/three.js sidecar) ->
              poster; model-viewer/three.js for live, orbit controls
              only while live.
- Audio:      waveform image (symphonia) -> poster; mini-player
              (Web Audio API + custom transport UI) for live.
- Web embed:  oEmbed/OpenGraph fetch or headless-browser screenshot
              (Node/puppeteer sidecar) -> poster; sandboxed iframe
              for live.
- Generic/unknown file: file-type icon + filename fallback poster;
              always downloadable even without a live renderer.

Node sidecar: only for 3D poster snapshots and web-embed screenshots
— tooling advantage, not a concurrency upgrade. Stub these jobs
early (generic file icon) and only stand up the sidecar once these
types are actively being built.

Feature-flagging: gate new/rough item types behind a simple flag
system so a half-finished renderer doesn't destabilize the main
board experience.

Onboarding checklist for a new item type (document in /docs):
  1. Add a backend ItemTypeHandler impl + register it.
  2. Add a frontend ItemRenderer (poster required, live optional)
     + register it.
  3. No core engine, schema migration, or canvas code changes required.
  4. Ship behind a feature flag if experimental.

SEQUENCING NOTE
========================================================================
Phases 1-4 (storage, ingestion, canvas engine) should be solid before
most of Phase 5+ feature work — this held true and is why the current
status shows those phases complete/near-complete while UI polish
(5-6), performance hardening (9), and extensibility (11) are still
open. The two foundational Phase 4 bugs (item drag delta math, note
edit-vs-move) are fixed and pinned by the gesture test suite
(frontend/tests + frontend/e2e); keep new interaction work behind the
same sampled-path tests before building Phase 11 on top.
