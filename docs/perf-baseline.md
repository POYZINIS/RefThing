# Perf Baseline — Phase 4 Canvas Engine

Baseline frame-time measurements for the Phase 4 canvas engine
(`frontend/src/canvas/BoardCanvas.ts`) against synthetic boards generated by
`frontend/src/dev/synthBoard.ts`. Recorded 2026-09-06.

## Machine

| | |
|:--|:--|
| CPU | AMD Ryzen 7 7800X3D (8 cores) |
| GPU | NVIDIA GeForce RTX 5080 (WebGL2 via ANGLE/D3D11 — real GPU, not SwiftShader) |
| RAM | 32 GB |
| OS | Windows 11 Pro |
| Browser | Chrome for Testing 153.0.8010.12 (Playwright chromium v1243, headless=new) |
| Viewport | 1920x1080 @ devicePixelRatio 1 |

## Method

Playwright drives headless Chromium to `/dev/board/<count>?seed=1&tour=1`
(the app mounts `DevBoard` there in dev builds; the standalone harness at
`/src/dev/board.html?count=…&seed=…&tour=1` is equivalent). The synthetic
board is deterministic per seed: 60% of items in Gaussian clusters / 40%
uniform over a `sqrt(count) * 2000px` extent, log-normal sizes 100–3000px, 15%
rotated ±15°, all items sharing ~200 procedurally generated placeholder images
(object URLs — no backend required). `?tour=1` runs a scripted 5s pan+zoom
tour (zoom 1 pan → zoom 0.15 overview pan → zoom 2 detail pan) and publishes a
JSON summary to the console and `document.title`. Frame times are sampled from
a requestAnimationFrame loop over the tour window.

Two runs per scale:

- **vsync-capped**: default headless frame pacing (~160Hz BeginFrame cadence on
  this machine) — measures whether real presented frames miss budget.
- **uncapped** (`UNCAPPED=1`, `--disable-frame-rate-limit
  --disable-gpu-vsync`): rAF runs free, so frame time reflects actual
  per-frame CPU cost instead of the pacing floor.

## Results (seed 1, 5s tour)

| Items | Run | Frames | Avg fps | Avg ms | p50 ms | p99 ms | Max ms |
|------:|:----|-------:|--------:|-------:|-------:|-------:|-------:|
| 5,000 | vsync-capped | 833 | 160 | 6.25 | 6.20 | 6.40 | 6.40 |
| 5,000 | uncapped | 10,276 | 1967 | 0.51 | 0.20 | 3.10 | 31.90 |
| 20,000 | vsync-capped | 834 | 160 | 6.25 | 6.30 | 6.40 | 6.40 |
| 20,000 | uncapped | 9,718 | 1875 | 0.53 | 0.20 | 3.40 | 32.70 |
| 50,000 | vsync-capped | 834 | 160 | 6.25 | 6.20 | 6.40 | 6.40 |
| 50,000 | uncapped | 9,869 | 1898 | 0.53 | 0.20 | 2.70 | 32.70 |

The vsync-capped rows sit flat at the ~6.25ms pacing floor for every scale —
no presented frame ever missed its slot. The uncapped rows show real per-frame
cost: ~0.5ms average, p99 under 3.4ms, flat across 5k→50k items (viewport
culling + grid-bucket index keep the working set constant). The ~32ms max is
a one-off hitch when the tour first enters a new cluster (texture decode +
GPU upload of placeholders not yet cached).

## Gate

**p99 frame < 16.6ms at 20,000 items: PASS** — p99 6.40ms vsync-capped
(~2.6x headroom), 3.40ms uncapped. No rbush swap needed at this scale; the
hand-rolled 512px grid-bucket index is not a bottleneck up to 50k items on
this hardware.

## Limitations

- `BoardCanvas` exposes no visible-sprite/texture counters, so the HUD and
  summaries report frame timing only.
- Placeholders are a single 256px image per hash shared across all pyramid
  levels, so level-swap decode cost is understated vs. real photos.
- Numbers are single runs on one machine; treat as a regression baseline, not
  an absolute guarantee.

## Reproduce

```sh
npm run dev -w frontend            # vite on :5173 (backend NOT required)
node frontend/src/dev/measure-perf.mjs http://localhost:5173 5000,20000,50000 1
UNCAPPED=1 node frontend/src/dev/measure-perf.mjs http://localhost:5173 5000,20000,50000 1
```

Each run prints `[refthing-perf] {json}` per scale; `gate.pass` is the p99 <
16.6ms verdict. Playwright + chromium are required (`npm i -D -w frontend
playwright && npx playwright install chromium`).


## Full-app frame timing (2026-09-24)

`node frontend/e2e/perf.mjs <count>` drives the real App (React chrome,
selection shell, previews, write queue) on a seeded board — unlike
`/dev/board/N`, which is canvas-only. Run it with `GPU=1` so Chromium
rasterizes on the GPU like the WebView2 shell; headless SwiftShader pins
every page at ~15fps regardless of content and is useless for timing.

20,000 items, GPU, frame intervals:

| Gesture                | p50    | p95    | p99    |
|:-----------------------|:-------|:-------|:-------|
| idle                   | 16.7ms | 16.8ms | 16.8ms |
| drag unselected image  | 16.7ms | 16.8ms | 33.3ms |
| drag selection shell   | 16.7ms | 16.8ms | 16.8ms |
| pan (middle drag)      | 16.7ms | 16.8ms | 16.8ms |

Pan was p95 33ms / p99 50ms before the rendered camera moved out of App
state (canvas/renderedCamera.ts): committing it per frame re-rendered the
whole shell.

The p99 blip on "drag unselected image" is the select-to-front write at
press time. Node objects are now cached per snapshot object (App and
BoardCanvas), the paint-order sort uses precomputed keys and the grid uses
numeric keys: the press costs ~90ms of dev-mode React work instead of ~141ms.
In the PRODUCTION build (what the desktop app ships), 10 presses on a
20k board: before 2/10 dropped one frame, after 1/10 (worst 33ms). Dev-mode
numbers overstate this cost several times over — measure production with
`vite build` + `vite preview` before optimizing further.
